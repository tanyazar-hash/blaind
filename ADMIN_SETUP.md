# BLΛIND ARENA · Supabase Auth

Проект: `https://ukihbdewnciurkaugtsd.supabase.co`. Панель: `/admin` (тихая ссылка «Управление» под подвалом).

URL и publishable key уже настроены в `server/config.js`. Это публичные идентификаторы проекта. Рабочие серверные запросы используют publishable key и JWT конкретного администратора; service-role / secret key не требуется. Пароли, Auth access/refresh tokens и приватные ключи в клиентский JavaScript не передаются.

## Однократное включение в Supabase Dashboard

Доступа к SQL Editor или Management API у приложения с publishable key нет. Эти действия выполняет владелец проекта:

1. **Authentication → Sign In / Providers**: оставьте вход по Email/Password, отключите **Allow new users to sign up** и **Anonymous Sign-Ins**. Если включены другие провайдеры, отключите их для этой панели. У посетителей и игроков нет регистрации, аккаунтов и форм входа. Отсутствие signup-кнопки не заменяет отключение регистрации в Supabase.
2. **Authentication → Users → Add user → Create new user**: создайте администратора с выбранным email и паролем; включите **Auto Confirm User**. При выключенной регистрации администраторов по-прежнему создаёт владелец через Dashboard. Пароль не вводится в SQL и не сохраняется в репозитории. Если нужный пользователь уже существует и подтверждён, используйте его.
3. В [SQL Editor](https://supabase.com/dashboard/project/ukihbdewnciurkaugtsd/sql/new) выполните `supabase/schema.sql`, затем `supabase/seed.sql`. Создаются таблица публичного содержимого, закрытый список администраторов, RLS и публичный бакет `arena-images` с загрузкой только администраторами. Миграция сохраняет существующий документ, а seed не перезаписывает записи.
4. В `supabase/add-admin.sql` замените `ADMIN_EMAIL_HERE` на email созданного пользователя и выполните этот файл в SQL Editor. Скрипт выдаёт права только уже существующему Auth-пользователю и не создаёт аккаунты / не отправляет письма. Передача пароля или service-role ключа приложению для этого не нужна.
5. После Git-деплоя откройте `/admin`, войдите по email и паролю. Измените тестовое поле, откройте `/arena` в другом окне и проверьте сохранение после обновления страницы. Затем проверьте тестовую загрузку афиши.

Для второго администратора повторите шаги создания Auth-пользователя и добавления его UUID в `arena_admins`. Новым обычным Auth-пользователям права администратора не выдаются автоматически. Данные `user_metadata`, домен email и наличие сессии сами по себе прав не дают.

## RLS и права

- `arena_documents`: `anon` и `authenticated` читают только запись `main`. Публичный документ содержит только данные рейтинга, турниров и публичные ссылки на изображения. Auth-пользователи могут изменять только `document` и `version`, только если присутствуют в `arena_admins`. Вставка и удаление всего документа через пользовательский API запрещены.
- `arena_admins`: авторизованный пользователь читает только собственное членство. `anon` не читает эту таблицу. У пользователей нет прав вставлять, изменять или удалять членство. Выдача прав — только владельцем через SQL Editor.
- `is_arena_admin()`: `SECURITY DEFINER`, фиксированный пустой `search_path`, все имена схем квалифицированы. Функция использует проверенный `auth.uid()`, а не поля профиля, и не позволяет менять список.
- `storage.objects`: публичное чтение объектов бакета `arena-images`; insert/update/delete только при `is_arena_admin()`. Политики ограничены этим бакетом. Изменение `bucket_id` в другой бакет запрещено данной политикой.
- Сервер заново проверяет Auth-пользователя и членство при каждом запросе; затем выполняет REST/Storage-запрос с его JWT, поэтому RLS действует и на серверный путь. Общий привилегированный ключ не используется для обхода политик.
- Для отзыва прав удалите UUID из `arena_admins`: это закрывает запись на уровне RLS и вход в редакторы при следующем запросе. Удаление Auth-пользователя также удаляет членство по внешнему ключу.
- Старые таблицы собственного входа, если были, не удаляются, но остаются закрытыми; код больше не использует их и прежние логин / пароль / хеш / секрет сессий.

## Сессии, сохранение и изображения

Supabase Auth проверяет пароль и подписанный access token, выполняет refresh и ограничение запросов входа. В браузере токены находятся только в HttpOnly SameSite=Strict cookie; на Vercel дополнительно Secure и префикс `__Host-`. Окно cookie — 8 часов, при активном refresh продлевается; точный срок access token и политика refresh задаются Supabase. Access token после logout может оставаться криптографически действительным до своего срока — это стандартное поведение Supabase; приложение очищает cookie и отзывает refresh текущей сессии. Для немедленного запрета записи удаляйте членство администратора.

Все изменения требуют Origin и CSRF-токен, редактирование — также актуальную версию документа. При конфликте введённые поля остаются в панели; скопируйте нужное перед обновлением. Все сохранения атомарны и доступны публичной странице без деплоя. Активные вкладки проверяют изменения каждые 4 секунды, при фокусе и через BroadcastChannel после сохранения в соседней вкладке. Изменение первого экрана не пересоздаёт неизменённые карточки турниров.

Изображения: JPEG/PNG/WebP до 3 МБ / 20 Мп, сигнатура и размеры проверяются сервером, SVG и анимация отклоняются, имена случайные. Предпросмотр локального файла доступен перед сохранением. Старые файлы удаляются после успешного сохранения и проверки ссылок. При ошибке очистки данные остаются сохранёнными; аварийное закрытие вкладки может оставить неиспользуемую загрузку в бакете — её можно удалить вручную. Подключите резервные копии согласно своему тарифу Supabase.

До создания таблицы / начальной записи публичная страница показывает прежнее демонстрационное содержимое; редакторы закрыты без Auth и членства. Ошибки сети, ключа, прав или работающей базы не подменяются демо-данными. Открытая страница при временном сетевом сбое сохраняет последний успешно показанный снимок.

## Переменные окружения и разработка

Для указанного проекта новые переменные Vercel не обязательны: публичная конфигурация уже в коде. Для другого проекта / окружения можно переопределить:

| Переменная | Значение |
| --- | --- |
| `SUPABASE_URL` | URL проекта HTTPS |
| `SUPABASE_PUBLISHABLE_KEY` | Его `sb_publishable_…` key, без привилегий service-role |
| `APP_ORIGIN` | Необязательно: production origin. В локальной среде и Preview оставьте пустым |

Прежние `SUPABASE_SERVICE_ROLE_KEY`, `ADMIN_USERNAME`, `ADMIN_PASSWORD_HASH`, `ADMIN_SESSION_SECRET` больше не используются; удалите их из настроек Vercel, если добавляли. Если старый `SUPABASE_URL` был задан вручную, он должен соответствовать указанному проекту или быть удалён.

`npm ci`; `npm run dev` запускает сервер на порту 8020 и при наличии читает `.env.local`. `npm run build` проверяет синтаксис и копирует только публичные ресурсы в `public`; код функций и конфигурация не публикуются статически. Vercel запускает две Node-функции `/api/arena`, `/api/admin`. GitHub Pages поддерживает только публичную статическую страницу без серверной панели.

`npm test` проверяет PostgreSQL-миграции через PGlite, реальные RLS под ролями anon/authenticated, запрет самоназначения, нескольких администраторов, отзы́в прав, CAS, CRUD, изображения и перезапуск базы. Вход/refresh тестируются на локальном Auth-симуляторе и отдельно на HTTP-контракте настоящего адаптера Supabase Auth; это не проверка входа в production.

`npm run test:browser` требует Playwright и Chromium `/usr/bin/chromium`; проверяет интерфейс с локальной тестовой базой, Auth-симулятором и RLS. Регрессия публичного интерфейса: `ARENA_BASE_URL=http://127.0.0.1:8020 node arena/tests/browser.cjs`. Production-подключение нужно проверить после выполнения SQL и создания Auth-администратора в Dashboard. Запреты сети среды не являются ошибками Supabase.


## Доступные редакторы

Панель содержит только «Игроки» и «Турниры». Первый экран арены фиксирован в публичном HTML, его редактор удалён, а `/api/admin?resource=hero` возвращает 404. Существующие legacy-поля `hero` и `settings` в базе сохраняются при каждой записи, чтобы не потерять прежние данные; первый экран больше их не использует. Авторизация, членство администраторов, RLS, формат документа, загрузка файлов и защита версий не изменены.

В турнире можно выбрать «Запланирован», «Идёт сейчас», «Завершён», «Отменён» и указать необязательное время окончания. Завершённые/отменённые и записи с прошедшим окончанием не показываются на публичной странице и не включаются в её счётчик. Старые записи без статуса и окончания исключаются после начала; для продолжающегося турнира выберите «Идёт сейчас». Это совместимые необязательные поля JSONB: выполнять новый SQL не нужно.
